# Backend HTTP Logging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Log every SpotWise backend HTTP request with method, path, status and duration, with contextual error logs, using `morgan`.

**Architecture:** Register a `morgan` middleware in the Express app before all routes with a custom format that uses `req.path` (never the raw URL, so query strings are excluded). Extend the existing central error handler to log a concise context line for every error response; keep the full stack trace for unexpected errors only.

**Tech Stack:** Express 4, TypeScript (`NodeNext`), `morgan`, `@types/morgan`, npm.

**Spec:** `docs/superpowers/specs/2026-11-17-backend-http-logging-design.md`

## Global Constraints

- Use `morgan`; do not replace it with a custom request logger.
- Every request is logged, including `GET /api/health`.
- Never log query strings, cookies, request/response bodies, passwords, OTP codes or base64 profile images.
- Keep existing startup, shutdown and DB-script logs unchanged.
- Do not change route behaviour, response shapes or authentication.
- Compiled output must remain `server/dist` via `tsc` (`npm run build`).
- No test framework exists in `server/`; verification is `npm run build` plus live requests against the running backend.

## Review Focus

- Query strings/tokens: a request to `/api/locations?status=Active` must log `/api/locations` only — covered by the live-request check in Task 1.
- Error context: a 404/unknown route and a 500/unexpected error must each produce a context line with method, sanitized path and status — covered by Task 2.
- Sensitive data: no cookie, body or query value appears in any log line — covered by the custom `:path` token and live inspection in Task 1.
- Duplicate/noisy logging: one request log line per request; the error context line is additional and does not replace it — covered by live inspection in Task 2.
- Build/runtime compatibility: `morgan` and its types compile under `NodeNext` TypeScript and `node dist/src/index.js` starts — covered by Task 1 build and startup check.

### Task 1: Install and register morgan request logging

**Files:**
- Modify: `server/package.json`
- Modify: `server/package-lock.json` (regenerated by npm)
- Modify: `server/src/index.ts`

**Interfaces:**
- Consumes: existing Express app and route registrations in `server/src/index.ts`.
- Produces: one stdout log line per completed request in the form `METHOD /path STATUS DURATIONms`.

- [ ] **Step 1: Install `morgan` and its types**

Run from `server/`:

```bash
npm install morgan
npm install --save-dev @types/morgan
```

Expected: `morgan` in `dependencies`, `@types/morgan` in `devDependencies`, lockfile updated.

- [ ] **Step 2: Register the middleware in `server/src/index.ts`**

Import `morgan`. After `app.use(cookieParser())` and before any route registration, register a `:path` token and the middleware:

```ts
morgan.token("path", (req) => req.path);
app.use(morgan(":method :path :status :response-time ms"));
```

Do not use morgan's built-in `:url` token (it includes query strings). If the type of `req` needs a cast to `express.Request` for `req.path`, use the narrowest cast possible; never fall back to `req.originalUrl`.

- [ ] **Step 3: Verify compilation and runtime logging**

Run:

```bash
cd server && npm run build
npm run dev
```

Expected: build exits 0; the server prints its startup line; `curl "http://localhost:4000/api/locations?status=Active"` prints exactly one line containing `GET /api/locations 200` followed by a duration; `curl http://localhost:4000/api/health` prints a `GET /api/health 200` line. Confirm no query string, cookie or body content appears in the log.

- [ ] **Step 4: Commit**

```bash
git add server/package.json server/package-lock.json server/src/index.ts
git commit -m "feat: log every backend HTTP request with morgan"
```

### Task 2: Add error context logging to the central error handler

**Files:**
- Modify: `server/src/middleware/error.ts`

**Interfaces:**
- Consumes: `HttpError` (`status`, `message`, `details`), Postgres error codes, existing `notFoundHandler(_req, res)` and `errorHandler(err, req, res, next)` signatures.
- Produces: one `[ERROR] METHOD /path STATUS message` line per error response; full `console.error("Unhandled error:", err)` stack only for unexpected errors.

- [ ] **Step 1: Add a shared context logger**

In `server/src/middleware/error.ts`, add a small helper `logErrorContext(req: Request, status: number, message: string)` that prints `[ERROR] ${req.method} ${req.path} ${status} ${message}`. Use `req.path` so query strings are never logged.

- [ ] **Step 2: Call the helper from every error response branch**

Rename `errorHandler`'s `_req` parameter to `req`. Call `logErrorContext` in the `HttpError` branch (its status/message), the `23505` branch (409 / `"A record with this value already exists"`), the `23503` branch (400 / `"Referenced record does not exist"`) and the final 500 branch (500 / `"Internal server error"`). Keep the existing `console.error("Unhandled error:", err)` in the final branch. Also call the helper from `notFoundHandler` (404 / `"Not found"`), renaming its `_req` to `req`.

- [ ] **Step 2: Verify error logging**

Run:

```bash
cd server && npm run build
npm run dev
curl -i http://localhost:4000/api/does-not-exist
```

Expected: build exits 0; the 404 response is unchanged (`{"error":"Not found"}`); logs show one `GET /api/does-not-exist 404` request line **and** one `[ERROR] GET /api/does-not-exist 404 Not found` line. Also confirm an unexpected error still prints the `Unhandled error:` stack trace.

- [ ] **Step 3: Commit**

```bash
git add server/src/middleware/error.ts
git commit -m "feat: log error context in backend error handler"
```
